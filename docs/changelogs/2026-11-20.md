
# Chat App Change Log

### Overview

Updated all three of the main speech tasks (`Map Task`, `Cooperative Planning`, and `Speech Elicitation`). All chats now have a separate call that checks:
1. Wether or not it thinks there was an ASR error that is *un-fixable* (bad enough that it can't use context clues to figure out what the user meant) and it needs to ask a follow-up clarification question before it can respond fully.
2. Wether or not the user's message was a "complete thought" and that it is likely that they finished their turn.

*There are more details on this new `reply_check` feature in a section below.*

The `Cooperative Planning` and `Map Task` chats now open with an intro, and end on their own (with a new "post-chat" screen with some info about how the session went). I also added a "debug mode" to the chat page that allows us to toggle certain behaviors on and off mid-chat and displays various timing information about the different backend processes so we can see where any delays come from.

**Detailed changes below:**

---

### **Listening & Replying:**

- **Backchannels:** When the participant pauses mid-sentence (time between words, according to ASR, > 0.70 seconds), the avatar (1) nods or tilts its head and (2) has a chance to use one of a few pre-set audible backchannels (e.g., "mm-hm"). In the `Map Task` and `Cooperative Planning`.

- **Reply check:** Before a reply goes out, a quick second check asks whether the participant had really finished, and whether a word was likely misheard. *(More details below.)*

- **More facial expressions:** The avatar can now actually picks from our wider set of the new reactions we added for each reply, such as a smile, a laugh, or a surprised or sympathetic look (before it just used a small arbitrary set that was limited to what the robots could do). Each task type uses its own set of options: 18 for `Speech Elicitation`, 13 for `Cooperative Planning`, and 5 for the `Map Task`. Most replies still get no reaction.


### **Changes to Specific Tasks**

- **Introduction (Map Task and Planning):** The avatar says hello, names the task, and asks whether the participant has done one before. It explains the rules only when needed and answers questions about them. The opening line itself is hardcoded, so all participants hear the same words.

- **Map Task ends itself:** The chat ends either (1) when the avatar reaches the finish point (or "close enough" to it), or (2) when the participant *says* that the avatar is there. In second case, befor ending, the avatar first says where it is (e.g., "I'm in the bottom left corner, below the saloon bar. Is that the finish?") and ends the chat if the user confirms.

- **Simpler agreeing in Planning:** It now puts stuff into the plan right away instead of always requring the user to confirm a second time (it felt super clunky to me when I had to do that, but we can still tweak this). This doesn't "lock in" any item permenantly though, any item can always be reopened for discussion. At the end of the task (once all three items have been added), the avatar recaps once: "So that's X, Y, and Z. Anything you'd change?" *I also made some changes to how the harness for this one works, so replies should come faster.*

- **Harnesses use context to understand (potentially) misheard ideas:** The harness compares words that appear as potential ASR errors to the ideas already discussed in the chat. For example, when I was testing it on one of the planning tasks, it had suggested we play "lo-fi" music. ASR heard my reply as "Yeah, go to love", but it was able to understood that I meant: "Yeah, go for lo-fi."

- **Speech Elicitation follow-ups:** The avatar tries to ask a few follow-up questions even if the user's answer is really short. It actually keeps a count of "at least 3 follow-ups" on a topic before changing the subject (for example, asking for an example, more details, or how it felt). If it get's a short answer from the user (I think 3 words or less), it asks an easier question on the same topic. It only intentionally moves on from a certain topic after it gets 2 short answers in a row.


### **After a Chat**

- **Chat end screen:** The chat page now stays open when a chat ends. It shows the chat's length, the message count, and a "Start a new chat" button. For the "information gap" tasks, it also reveals what the participant couldn't see during the task: the avatar's map and path (`Map Task`) or its brief/objective and constraints (`Cooperative Planning`). For the `Speech Elicitation` task, it just shows a list of the topics covered.

- **Admin "Completed Chat" Page Overhaul:** The old "Completed Chat" details page that you could see when clicking on a `ChatSessionCard` in the Admin page was redesigned for the new chat types. The initial design is still pretty similar, but for chats using any of our three speech tasks, there is now a button that will take you to a second, task-specific details page. Each of these has some general chat info, plus additional stuff relevant to it's specific task and harness:
  - Map Task: both maps overlaid, and how close the avatar got to the finish.
  - Planning: who suggested each choice, and which ideas were turned down.
  - Speech Elicitation: the topics covered, and the follow-ups on each.


### **Debug Mode**

Each user account now has an attribute that turns on "debug mode" for the chat page. Admin users can toggle this on or off (*I think there is actually a bug with this right now where you guys can't see this yet*).
- This adds a "debug panel" to the page that has on/off switches for subtitles, cues, backchannels, and each of the two parts of the `reply_check` feature.
- It also adds some timing labels that show in real time how long each system in the backend takes: the delay between you and the backend server, the delay from each LLM call (separate numbers for the `reply_check` and response generation calls; they run simultaneously), the delay added by TTS synthesis, and the total delay (time between the end timestamp of the last word recognized by ASR and the first chunk of the avatar's audio being spoken).

Each reply's timing is saved and shown on the admin pages, and the admin live page has the same switches.


## How the new `reply_check` feature works

When a participant stops talking, the system now sends two requests to the LLM at the same time instead of one:

1. **Standrad reply request:** This is the normal reply request where we have the avatar think about the current context, decide what it should say in response to the user's last message, and pick an expression/animation to show.

2. **The `reply_check` call:** This is a much shorter prompt that asks two things:
    - **(a)** Does the user's speech imply that they've fully finished their thought (and therefore their turn)?
    - **(b)** Based on the current conversation's context, is it likely that ASR misheard a word? *and is the misrecognition bad enough that we can't figure out what they meant to say through context?*

Because the `reply_check` call is so much shorter, it almost always finishes before the stanard reply call. Since the two requests run side by side, the `reply_check` adds almost no delay. By the time the reply is ready, the verdict is usually waiting. Once the check finishes, one of three things happens:

| Verdict | What happens |
| --- | --- |
| **Reply** | The answer goes out as usual. |
| **Wait** | The participant seems to be mid-thought. The avatar nods or says "mm-hm" and holds the reply for 2 seconds (2.5 in Speech Elicitation). If the user continues talking before the wait is over, the reply is cancelled. If they stay quiet, the reply that was already written goes out. |
| **Clarify** | A likely misheard word hides what the participant meant, so the avatar asks about it instead (e.g. "Sorry, did you say 'X'?"). |

Each task type gives the check its own "hints". The `Map Task` check knows the landmark names on both maps, and the `Cooperative Planning` check knows about all of the current ideas that have been discussed (food names, or otherthings that might be more difficult words for ASR).

The check never leaves the avatar silent. If it fails, or is still running 1 second after the reply is ready, the reply goes out unchecked.
